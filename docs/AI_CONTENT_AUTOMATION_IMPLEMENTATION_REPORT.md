# تقرير تنفيذ Luminous Derma — Content Intelligence وAutomation

## النطاق المنفذ

تم تطوير النظام فوق مركز المحتوى ومركز المحتوى المرئي الموجودين، دون إنشاء VisualComposer بديل أو تكرار Content-Ops. بقيت دورة النشر محكومة بالمراجعة اليدوية، ولم يتم إنشاء أو نشر منشورات حقيقية.

## ما تم إصلاحه

تم إصلاح مسار حفظ المحتوى المرئي بحيث تحفظ آخر نسخة حررها المستخدم فعليًا، بما يشمل الخطاف، العنوان، العنوان الفرعي، النص، زر الإجراء، التسمية التوضيحية، والهاشتاغات. قبل هذا الإصلاح كان زر الحفظ يرسل المعرّف فقط، ثم يعيد مسار Content-Ops التوليد من النص الأصلي؛ لذلك كان يمكن أن تضيع تعديلات المستخدم. أصبح الحفظ الآن يمر عبر `update-copy`، ثم تُستخدم النسخة المحفوظة نفسها عند الترقية إلى `REVIEW_REQUIRED`.

تمت إضافة فحص Claim Safety على النص المعدل، ومنع تعديل السجل بعد بدء النشر أو بعد النشر، وإعادة استخدام عنصر Content-Ops الموجود بدل إنشاء عنصر مكرر عند إعادة الحفظ.

## الفصل بين الفكرة والتصميم

أضيف سجل مستقل لـ35 Content Pillars في `src/lib/content-ops/monthly-simulation.ts`. هذه الـPillars تمثل موضوعات تحريرية فقط، ولا ترتبط بقالب بصري ثابت. يظل اختيار Creative Direction منفصلًا، ويستخدم كتالوج Visual Studio الحالي للتنويع.

## المحاكاة الشهرية

أضيف مسار قراءة فقط:

`GET /api/admin/content?action=monthly-simulation&days=30`

المحاكاة تنتج 60 خانة نظرية، بمعدل منشورين يوميًا، وتتحقق من:

- تغطية الـ35 Pillars.
- وجود منشور Discovery يوميًا.
- تنويع المنتجات.
- تنويع Creative Directions.
- عدم تكرار Creative Direction في منشورين متتاليين.
- بقاء كل النتائج في `REVIEW_REQUIRED`.
- عدم الكتابة إلى Content-Ops أو Scheduling أو Publishing.

## الأتمتة والنشر

النظام الحالي يحتوي أصلًا على مراحل Generate، Validate، Review، Approve، Schedule، Publish، Analytics، وإعادة المحاولة مع مفاتيح idempotency. الإعدادات الافتراضية الحالية تؤكد أن:

- `autoGenerate = false`
- `autoSchedule = false`
- `autoPublish = false`
- القناة المتصلة افتراضيًا هي `website` فقط.

فحص إعدادات الجلسة لم يجد موصلات Meta أو Instagram باسم ظاهر في `config.json`. لذلك لم يتم الادعاء بأن القنوات الاجتماعية متصلة، ولم يتم تفعيل أو اختلاق اتصال بها. عند توفر الموصل الحقيقي يجب ربطه من إعدادات الجلسة ثم إبقاء النشر خلف موافقة الإدارة.

## البيانات وقاعدة البيانات

لم يتم تنفيذ INSERT أو UPDATE أو DELETE يدوي على Supabase أثناء هذه المرحلة، ولم يتم تعديل المنتجات أو الأسعار أو الصور أو المخزون. المحاكاة لا تحفظ سجلات حقيقية. لذلك لا توجد Migration جديدة مطلوبة لهذه المرحلة.

## التحقق

تمت مراجعة مسارات API، أنواع Content-Ops، دالة `editItem`، سجل Visual History، طبقة Claim Safety، إعدادات النشر، وكتالوج Visual Studio. تعذر إكمال `tsc` و`git diff` من خلال بيئة المسار المركب لأن عملية Node على FUSE بقيت معلقة دون مخرجات، وتم إيقافها بدل إعادة تشغيلها عشوائيًا. يجب تشغيل الفحص محليًا من PowerShell داخل مجلد المشروع:

```powershell
npm run lint
npx tsc --noEmit
npm run build
```

ثم اختبار المسار التالي بحساب Admin:

```text
/admin/ai/content/visual
```

مع توليد منشور، تعديل جميع الحقول، الضغط على «حفظ كمسودة للمراجعة»، ثم فتح عنصر Content-Ops والتأكد من ظهور النسخة المعدلة لا النسخة الأصلية.

## المطلوب قبل النشر الحقيقي

الخطوة الوحيدة المطلوبة لاحقًا هي تزويد النظام ببيانات اعتماد Meta/Instagram الحقيقية عبر الموصل المخصص، ثم اختبار منشور واحد يدويًا بعد الموافقة. لم يتم تفعيل النشر التلقائي، ولم يتم إنفاق أي ميزانية إعلانية أو إنشاء حملة مدفوعة.
